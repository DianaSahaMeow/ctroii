# СтройКонтроль — Система приемки квартир и учета строительных дефектов

Полнофункциональная инженерная система для технического надзора, приемки квартир и учета строительных замечаний на объектах капитального строительства.

---

## 1. Технологический стек

- **Бэкенд:** Java 17+, Spring Boot 3.3.5, Spring Security 6 (ролевая модель `WORKER` / `MANAGER`), Spring Data JPA, Hibernate 6.
- **База данных:** PostgreSQL 16 (с поддержкой миграций Flyway и ANSI SQL совместимостью с H2 для мгновенного локального запуска).
- **Хранилище фото:** Локальное файловое хранилище на сервере с раздачей статики и HTTP-кэшированием + архитектурная абстракция `StorageService` с заготовкой под S3 / MinIO / Cloudflare R2.
- **Фронтенд:** Адаптивный Mobile-First интерфейс на чистом HTML5 / CSS3 / Vanilla JS (SPA) без тяжелых зависимостей (node_modules не требуются, собирается и раздается напрямую из Spring Boot JAR).
- **Сжатие изображений:** Двухуровневое сжатие (клиентское через HTML5 Canvas перед отправкой + бэкенд-контроль через Thumbnailator) для мгновенной работы на мобильном 3G/LTE на стройплощадке.

## 3. Бизнес-логика и архитектурные решения

### Уникальность квартиры
Квартира однозначно идентифицируется связкой:
`entrance_number` (номер подъезда, Integer) + `apartment_number` (номер квартиры, Integer).
В базе данных наложен уникальный констрейнт:
```sql
CONSTRAINT uk_entrance_apartment UNIQUE (entrance_number, apartment_number)
```

### Накопительный учет (Плюсование)
При фиксации замечания система проверяет наличие квартиры по связке `(подъезд, квартира)`:
1. Если квартира уже существует в базе (включая квартиры со статусом «В архиве»):
   - Новая запись **не создает дубликат квартиры**;
   - Замечание привязывается к существующей карточке квартиры;
   - Если квартира находилась в архиве (`is_archived = true`), она **автоматически разархивируется (`is_archived = false`)** и возвращается в активный дашборд руководителя со статусом «В работе».
2. Если квартиры еще нет в базе — автоматически создается новая карточка.

### Карточка квартиры
Внутри карточки отображается журнал по объекту:
- **Сверху:** Активные дефекты (статусы «НОВЫЙ», «В РАБОТЕ», «ИСПРАВЛЕН») с фотографиями, описанием, автором, датой фиксации, селектором срочности и селектором статуса.
- **Снизу:** История закрытых и принятых замечаний (статус «ПРИНЯТ») с датами закрытия и фотофиксацией.
- **Кнопка «Отправить в архив»:** Активируется **только тогда**, когда все дефекты по квартире переведены в статус «ПРИНЯТ».

### Фотофиксация и оптимизация трафика
1. На смартфонах рабочие делают снимки высокого разрешения (12-48 Мп, 5-15 МБ).
2. Модуль `image-compressor.js` перехватывает файлы на клиенте, масштабирует на `<canvas>` до максимальной стороны 1400px и сжимает JPEG до 82% качества.
3. Размер файла уменьшается до 250-400 КБ без потери деталей дефекта, отправка по мобильной сети занимает доли секунды.

## 5. Быстрый запуск

### Вариант 1: Мгновенный локальный запуск (H2 в режиме PostgreSQL)
Не требует установки сторонних СУБД. База данных сохраняется в файл `./data/defectdb`.
```powershell
mvn spring-boot:run
```
Откройте браузер: [http://localhost:8080](http://localhost:8080)

### Вариант 2: Запуск в Docker Compose (с PostgreSQL 16)
```bash
docker compose up -d --build
```
Поднимаются контейнеры `defect_tracker_db` (PostgreSQL 16) и `defect_tracker_app` (Spring Boot).

### Вариант 3: Бесплатное облачное развертывание
Подробная пошаговая инструкция по бесплатному деплою на **Neon.tech (PostgreSQL)** + **Render.com (Бэкенд)** описана в файле [FREE_HOSTING_GUIDE.md](file:///c:/Users/Никита/Desktop/папа/FREE_HOSTING_GUIDE.md).

## 6. Структура REST API

- `POST /api/auth/login` — вход в систему (стандартный Spring Security Form Login с ответом JSON).
- `GET /api/auth/me` — данные текущего пользователя.
- `POST /api/auth/logout` — выход из системы.
- `GET /api/dashboard/metrics` — метрики дашборда (квартир в работе, открытых дефектов, срочных, закрытых за месяц).
- `GET /api/dashboard/calendar?year=YYYY&month=MM` — количество зафиксированных дефектов по дням месяца.
- `GET /api/apartments?archived=false` — реестр квартир в работе.
- `GET /api/apartments?archived=true` — архив принятых квартир.
- `GET /api/apartments/{id}` — полная карточка квартиры (активные + принятые дефекты).
- `POST /api/apartments/{id}/archive` — перевод квартиры в архив (только если все дефекты приняты).
- `GET /api/apartments/entrances` — список уникальных номеров подъездов.
- `POST /api/defects` — создание дефекта (multipart/form-data: `entranceNumber`, `apartmentNumber`, `description`, `urgency`, `photos`).
- `GET /api/defects/my` — список дефектов, заведенных текущим рабочим.
- `GET /api/defects/by-date?date=YYYY-MM-DD` — список дефектов за выбранный день (для календаря).
- `PATCH /api/defects/{id}/status` — изменение статуса дефекта (только MANAGER).
- `PATCH /api/defects/{id}/urgency` — изменение уровня срочности дефекта (только MANAGER).
- `POST /api/defects/{id}/comments` — добавление записи в оперативный журнал работ по дефекту (автор, роль, текст).
- `GET /api/dashboard/efficiency` — расчет КПД и расширенная аналитика эффективности (общий %, по срочным %, среднее время устранения MTTR, баланс недели Velocity, выработка приемщиков).
- `GET /api/files/{fileName}` — безопасная отдача фотографий с кэшированием.

## 7. Модуль аналитики КПД и оперативный журнал работ

1. **Расчет КПД и метрик эффективности (`/api/dashboard/efficiency`):**
   - **Общий КПД устранения (%):** Доля дефектов в статусе «ПРИНЯТ» от всех когда-либо зарегистрированных замечаний.
   - **КПД по срочным дефектам (%):** Результативность устранения критических замечаний с наивысшим приоритетом.
   - **Среднее время устранения (MTTR):** Точный расчет средней длительности устранения дефекта от момента фиксации до перевода в статус «ПРИНЯТ» (в часах и рабочих днях).
   - **Недельный темп устранения (Velocity):** Соотношение поступивших новых замечаний к числу закрытых за последние 7 дней (статусы «ОПЕРЕЖЕНИЕ», «ПАРИТЕТ», «ОТСТАВАНИЕ»).
   - **Таблица выработки приемщиков:** Число выявленных замечаний, количество срочных позиций, закрытые замечания и персональный процент закрытия по каждому инженеру/приемщику.

2. **Оперативный рабочий журнал дефекта:**
   - В карточке каждого дефекта ведется хронологическая лента действий.
   - Руководитель и приемщики могут оставлять оперативные записи с указанием автора, должности и точного времени (например: *«Отправил бригаду сантехников. Обещали устранить до 18:00»*, *«Заказан стеклопакет»*).
   - Быстрые шаблоны в 1 клик для удобства работы с мобильного телефона:
     - `+ Отправил бригаду`
     - `+ Заказаны материалы`
     - `+ Подрядчик устранил`
     - `+ Повторный осмотр`
